Ranking Content for Refresh Review from Observable Search Signals

Yuan Andrei C. Mariano · Computer Science, Specialization in Data Science
Public repo: github.com/yuan05-afk/flyrank-ml-internship

Abstract

Editors need a short, honest queue of which pages to refresh first. Using a 30,000-row anonymized FlyRank starter snapshot (32 clients; trailing-90-day search and engagement metrics), this work frames refresh prioritization as a ranking task with an observed decline label, a transparent rule baseline, and client-holdout validation. A random forest selected by Precision@50 reaches 0.74 on the holdout versus 0.24 for the baseline (base rate ≈ 0.54; ROC-AUC ≈ 0.75). The output is a ranked review queue with scores, actions, and reason codes for human triage, not an automatic publishing decision or a claim about Google’s ranking algorithm.

1. Introduction / Problem

Content sites accumulate pages faster than editorial capacity. The decision this project supports is: which existing pages should an editor open for refresh review this week? The unit of analysis is one content item (page). The action is to prioritize rewrite or expansion effort. A wrong call wastes rewrite hours (false positives) or leaves declining, still-visible pages untouched (false negatives).

A single threshold rule (for example, “stale and high impressions”) is a fair starting point and remains the reason-code layer of the playbook. It is not enough when CTR gaps, thin depth, staleness, and visibility interact differently across clients. Machine learning earns a place only if it beats that transparent baseline on the same split and the same operational metric.

2. Data

Primary dataset: data/raw/content_refresh_anonymized.csv — 30,000 rows × 44 columns, one row per pseudonymized content item, 32 clients, trailing-90-day aggregates. Full column meanings are in the repo data dictionary.

Warehouse (deferred): Hugging Face FlyRank/internship-warehouse (~79M daily performance rows) was not queried in this environment (no HF token / gate access in the build machine). The contract and notebooks are complete on the starter release; SETUP.md documents requesting warehouse access for panel extensions.

Excluded on purpose: trend_direction and trend_pct as features (they define the decline label); content_id / client_id as features (grouping and client-holdout only); any client names, URLs, or private queries (not present in the starter; never invented).

Gotchas respected: rate columns are ×100 percentages; avg_position = 0 means missing rank, not rank zero.

3. Methodology

3.1 Label

is_declining_label is an observed proxy: positive when trend_direction is down in the snapshot. It is not an editorial ground truth and not a future sealed warehouse window.

3.2 Features

Numeric and categorical lists follow scripts/ml_utils.py (impressions/clicks/sessions transforms, freshness, CTR, position, content tiers, and related categoricals). Leakage hunt: forbidden fields do not appear in the model feature lists.

3.3 Baseline

Transparent score combining visibility (impressions rank), freshness risk (days since update), and a CTR-gap flag on visible ranked pages. Emits a primary reason code and action label (refresh, refresh_and_review_ctr, monitor).

3.4 Models and split

Logistic regression, decision tree, and random forest. Split: client-holdout (entire clients held out for test). Selection metric: Precision@50. Seeds fixed at 42 in experiment notebooks; reference pipeline via python scripts/run_all.py.

Base rate (declining label): ≈ 0.542. Precision@50 must be read next to that base rate and the baseline.

Top RF importances are dominated by impression presence and volume, average position, and content age — signals an editor already reasons about, reweighted jointly. Errors still happen: high-impression stable pages can rank high (false positives); low-volume declines can be missed. That is why the playbook requires human review.

5. Limitations and honest framing

  • Snapshot label, not a sealed future window from the warehouse panel.
  • Starter sample size; warehouse access deferred without HF credentials in this build.
  • No causal claim that refreshing recovers traffic — that needs an experiment design.
  • No claim of predicting Google’s algorithm.
  • Rate-scale and missingness gotchas can mislead naive feature engineering.

6. Ranked recommendations (action playbook)

  1. Open high-confidence refresh / refresh_and_review_ctr rows first.
  2. Verify on-page context; apply the no-go list (legal freezes, YMYL caution, no auto-publish).
  3. Treat monitor as backlog, not rewrite fuel.
  4. Retrain or freeze when holdout Precision@50 drifts toward the baseline across refreshes.

Full playbook notebook: w07_action_playbook.ipynb
